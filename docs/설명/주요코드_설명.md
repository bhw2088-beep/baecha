## 2. 화물 등록 → 기사 제안까지 (한눈에)

```
화주 등록 (POST /shipper/orders)
  ① 서버 적재 검증      packer.service.plan()          → 전량 적재 + 규칙 위반 없음일 때만 등록
  ② 매칭 라운드          matching_service._matching_round()  (Redis 분산 락 안)
       ├ 하드 필터        승인 · 노란 번호판 · 블랙리스트 · 기사 톤수 ≥ 필수 톤수 · PostGIS 반경
       ├ 차량별 적재 재계산  _fit() → 그 기사 차량에 정말 다 실리는가 (차종별 캐시)
       ├ 점수            규칙(거리 60% + 적재율 40%) 70% + LightGBM 수락 예측 30%, 0.75 미만 제외
       └ 최적 배정        hungarian.assign()  대기 화물 전체 × 빈 차 전체
  ③ 제안 → 기사 수락 (60초 안) → 배차 확정 / 거절 · 시간 초과면 다음 라운드에서 다음 기사
```

**측정 (컨테이너 · 시드 기사 17명 + 빈 차 12대 · 대기 화물 7건 동시 배정)**

| 단계 | 팔레트 혼적 63상자 | 콜드체인 58상자 | 다중 하차 29상자 |
|---|---:|---:|---:|
| ① 서버 적재 검증 | 171 ms | 80 ms | 49 ms |
| ② 매칭 라운드 전체 | 284 ms | 314 ms | 110 ms |
|   ㄴ 차량별 적재 재계산 | 271 ms | 300 ms | 96 ms |
|   ㄴ 도로 거리 (112회) | 5.5 ms | 5.6 ms | 5.4 ms |
|   ㄴ LightGBM 예측 | 1.5 ms | 1.7 ms | 2.0 ms |
|   ㄴ **헝가리안 배정** | **< 0.1 ms** | **< 0.1 ms** | **0.1 ms** |
| **등록 → 제안 합계** | **0.46초** | **0.39초** | **0.16초** |

→ 시간 대부분은 "이 차에 정말 다 실리는가"를 3D로 다시 계산하는 데 쓰입니다. 최적 배정 자체는 1 ms 미만입니다.
관제 '매칭 분석'의 **평균 배차 소요**는 `기사 응답 + 시스템 매칭(실측)`으로 나눠 보여 줍니다 (데모: 38초 = 응답 38초 + 매칭 0.23초).

## 3. 3D 적재 엔진: 규칙 + Extreme Point

### 3-1. 규칙표 — 엔진 · 검증기 · 화면이 같은 번호를 쓴다
[`rules.py`](../../backend/src/engines/packer/rules.py)

```python
RULES: tuple[Rule, ...] = (
    Rule("R0", "compat", "차량-화물 호환", "냉장 화물은 냉장 차량에만", "check"),
    Rule("R1", "bounds", "적재함 경계", "모든 상자가 적재함 안쪽", "place", "남은 공간 부족"),
    Rule("R2", "overlap", "상자 간 비중첩", ...),
    Rule("R3", "orientation", "방향 (세움 고정)", ...),
    Rule("R4", "weight", "최대 적재중량", ...),
    Rule("R5", "support", "지지면 (안정성)", ...),          # 바닥 80% 이상이 닿아야 (공중 부양 금지)
    Rule("R6", "stacking", "적층 · 상부 허용하중", ...),     # 허용하중의 90%까지만 (10% 여유 · TOP_LOAD_MARGIN)
    Rule("R7", "top_only", "최상단 배치 (파손주의 · 냉동)", ...),
    Rule("R8", "lifo", "하차 순서 (LIFO)", ...),
    Rule("R9", "safety", "보수적 안전율", ..., "place", "안전율 한도 초과 (더 큰 차량 필요)"),
    Rule("R10", "cog", "축중량 균형 (산안법 제173조)", ..., "balance"),
)
```

| 적용 단계 (`stage`) | 규칙 | 의미 |
|---|---|---|
| `place` 배치 중 차단 | R1~R9 | 어기는 자리에는 아예 놓지 않음 |
| `balance` 배치 중 선택 | R10 | 놓을 수 있는 자리가 여럿이면 좌우 균형이 맞는 쪽 |
| `check` 결과 판정 | R0 · R10 전후 | 배치 후 채점만 |

- **왜:** 엔진 · 검증기 · 화면 · 미적재 사유가 각자 문구를 가지면 서로 어긋납니다. 규칙 하나를 바꾸면 모두 같이 바뀌도록 한 곳에 모았습니다.
- 미적재 사유도 `"R5 지지면 부족 (공중 부양 위험)"`처럼 규칙 번호로 나옵니다.

### 3-2. Extreme Point 탐색 + R10 좌우 균형
[`engine.py`](../../backend/src/engines/packer/engine.py) — Crainic · Perboli · Tadei (2008) Extreme Point 휴리스틱

```python
def _first_fit(self, box, eps, fails):
    for ep in eps:                                   # 후보점(EP)을 우선순위(벽 쌓기 / 바닥 우선) 순서로
        best = None
        for dx, dy, dz in box.orientations():        # 허용 방향 (세움 고정이면 수직축 회전만 = R3)
            cand = self._try(box, ep, dx, dy, dz, fails)   # R1 경계 · R2 겹침 · R5 지지 · R6 하중 · R7 · R8
            ...
        if best:
            cand = best[1]
            if self.o.balance:                       # R10: 같은 줄 반대편에도 놓아 보고
                alt = self._mirror(box, cand)
                if alt is not None and self._lateral_after(alt) + EPS < self._lateral_after(cand):
                    alt.balanced = True
                    return alt                       # 좌우 무게중심이 가운데에 더 가까운 쪽
            return cand
```

- **EP(Extreme Point):** 상자를 놓은 뒤 세 모서리를 벽 · 다른 상자 쪽으로 '투영'해 새 후보점을 만듭니다. 이미 놓인 상자 모서리만 쓰는 방식보다 빈틈을 잘 찾습니다.
- **R10 반대편 배치:** EP는 왼쪽 벽부터 채워서 그대로 두면 한쪽으로 쏠립니다. 같은 x · z 줄에서 오른쪽 벽(또는 오른쪽 상자 옆)에 붙인 자리도 시험해 무게중심이 가운데로 오는 쪽을 고릅니다.
- **충돌 · 지지면 검사는 numpy 벡터 연산:** 이미 놓인 상자 전체와 한 번에 비교합니다.

```python
# R2 비중첩 — 놓인 상자 k개와 한 번에
if k and np.any((X0 < x + dx) & (X1 > x) & (Y0 < y + dy) & (Y1 > y) & (Z0 < z + dz) & (Z1 > z)):
    fails["space"] += 1
    return None
```

### 3-3. R9 안전율 · R6 상부 하중 여유 · 균형 배치 폴백
[`engine.py`](../../backend/src/engines/packer/engine.py) · [`service.py`](../../backend/src/engines/packer/service.py)

```python
# R9: 엔진이 처음부터 (1 − 안전율 5%) = 95% 까지만 싣는다
cap = 1 - max(0.0, self.o.safety_margin)
self.weight_limit = self.c.max_weight * cap
self.volume_limit = self.c.volume * cap

# R6: 상자 위에 쌓는 하중은 허용하중 × (1 − 여유 10%) = 90% 까지만 — 신고 무게가 실제보다 가벼워도 견디게
k_cap = 1 - max(0.0, self.o.top_load_margin)
caps = [p.box.cap * k_cap for p in self.placed] + [box.cap * k_cap]

# service._run: 균형 배치 결과가 '전량 적재 + 위반 없음'이 아니면 균형 없이 한 번 더 → 더 나은 쪽
r = _run_once(container, boxes, options, cold_chain)
if options.balance and not _ok(r):
    r2 = _run_once(container, boxes, replace(options, balance=False), cold_chain)
    if _score(r2) > _score(r):
        r = r2
```

- **왜 R6 여유:** 엔진은 화주가 신고한 무게로 계획을 세웁니다. 신고 무게가 실제와 −5 ~ +10% 다르다고 보고 8,008건을 다시 재 보니, 여유 없이(허용하중 100%까지) 쌓으면 품목 배차 2,200건 중 **797건(36.2%)** 에서 아래 상자의 상부 하중이 실제로는 허용하중을 넘었습니다(최대 +10%). 허용하중의 90%까지만 쌓도록 바꾼 뒤 **0건**이 됐고, 적재율(62.1%) · 매칭 성공률(91.5%)은 그대로입니다. 무작위 화물 10,000건([`backend/tests/stress_tests/5_packing_stress.py`](../../backend/tests/stress_tests/5_packing_stress.py))에서도 같은 오차로 상부 하중 초과가 938건 → 0건이 됐습니다 (대가: 더 큰 차 필요 52건 · 등록 불가 42건, 8장 참고). 여유 비율은 설정 `TOP_LOAD_MARGIN` 으로 바꿀 수 있습니다 (비교 실행: [`backend/tests/stress_tests/3_margin_compare.py`](../../backend/tests/stress_tests/3_margin_compare.py)).
- **왜 폴백:** 균형 배치는 상자마다 그 순간 최선을 고르는 방식이라 드물게 전체 결과가 나빠질 수 있습니다. 174개 경우 비교에서 폴백을 넣은 뒤 **나빠진 경우 0건**, 성공 90 → 95건, 좌우 편차 평균 7.1% → 4.2%.

### 4-2. ② 점수: 규칙 70% + LightGBM 수락 예측 30%
[`matching_service.py`](../../backend/src/services/matching_service.py) · [`ml_ranker.py`](../../backend/src/engines/matcher/ml_ranker.py)

```python
def match_score(pickup_km, util, radius_km=50, w_dist=0.6) -> float:
    """0~1. 가까울수록(반경 대비), 적재함을 많이 채울수록 높다."""
    dist = max(0.0, 1 - pickup_km / radius_km)
    return round(w_dist * dist + (1 - w_dist) * max(0.0, min(1.0, util)), 4)

def _combine(self, rule, ml):
    return round((1 - ML_WEIGHT) * rule + ML_WEIGHT * ml, 4)        # ML_WEIGHT = 0.3

r["lgb_pass"] = p >= ML_THRESHOLD    # 0.75 미만이면 자동 제안 안 함 (거절될 제안을 미리 차단)
```

| 요소 | 내용 |
|---|---|

| 가중치 | 거리 60% · 적재율 40% — 관제 '자동 매칭 설정'에서 바로 변경 |

**적재 · 과적 KPI — 무작위 화물 10,000건**

8,008건 실행의 적재 검증(배차 2,200건)은 샘플 화물 3종을 반복한 것이라, 적재 KPI는 무작위 화물로 따로 잽니다.

- **과적(총중량 초과)은 상부 허용하중 여유와 상관없이 거의 같습니다** — 총중량은 R9 안전율(최대 적재량의 95%까지만)이 정하기 때문. 실제 무게가 신고보다 5% 넘게 무거워야 생기고, 오차 +5% 이내(±5%)면 0건입니다.

- **상부 하중 초과는 오차가 +10% 이내면 여유 10%가 전부 흡수합니다** (−5 ~ +10%: 938건 → 0건). ±15%에서는 90건이 남고, 여유 15%여야 0건이 됩니다.
- 여유 10%에서 남는 위험은 상부 하중이 아니라 **총중량 초과**(신고 기준 95%까지 실었는데 실제가 5% 넘게 무거운 경우)와 **축중량**(실제 무게가 달라 무게중심이 밀림)입니다 — 신고 무게만으로는 막을 수 없어 계근 · 상차 검수가 필요한 영역.
- 대가는 작습니다: 여유 10%로 더 큰 차가 필요해진 화물 52건 · 새로 등록이 안 되는 화물 42건 (정상 화물 8,508건의 0.6% · 0.5%). 평균 적재율(부피 28.7% · 중량 55.8%)과 적재 계산 시간(평균 0.58초)은 거의 그대로.

**측정하면서 고친 것**
- **DB 저장 묶음** ([`main.py`](../../backend/src/main.py)): 예전엔 변경 요청(POST)마다 메모리 데이터 전체를 바로 저장해 그동안 다른 요청이 줄을 섰다
