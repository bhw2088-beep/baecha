- 여유 10%에서 남는 위험(−5~+10%: 과적 23 · 축중량 32건)은 신고 무게만으로는 막을 수 없는 영역 → **계근 · 상차 검수**가 필요.
- 대가는 작습니다: 여유 10%로 더 큰 차가 필요해진 화물 52건 · 새로 등록이 안 되는 화물 42건 (정상 화물 8,508건의 0.6% · 0.5%). 적재율 · 계산 시간은 거의 그대로.
- 정상 화물 14.3%가 등록되지 않는 주된 사유는 R7 최상단 전용(파손주의 · 냉동) 품목 과다 · R6 적층 불가 품목 위 적재 · 공간 부족 · 지지면 부족 — 규칙상 그대로는 안전하게 못 싣는 화물.

## 4. 오탐 방지 설계와 결과

### 4-1. 물리적 적재 오탐 (Rule + Extreme Point)
| 규칙 | 기준 | 위치 |
|---|---|---|
| 보수적 안전율 (5%) | 부피 · 중량 90% 초과 경고, 95% 초과 차단 (10%에서 완화 — 지나치게 방어적인 배차 방지) | `engines/validation_engine.py` |
| 축중량 균형 (산안법 제173조 편하중 방지) | 좌우 편차 10% 경고 · 15% 차단, 전후 무게중심 20~65% 정상 · 15~75% 밖 차단 (경량 화물은 경고로 완화) | 〃 |
| 상하적재 · 파손주의 · LIFO | 상부 하중 ≤ 허용하중의 **90%** (10% 안전 여유 — 신고 무게 오차 흡수) · 적층 금지 · 하차 순서 가로막힘 | `engines/packer/engine.py` · `validate.py` |
| 필수 최소 톤수 | 안전율 적용 총중량 · 총부피 → 가장 작은 표준 차량 톤수 → 매칭 하드 필터 | `validation_engine.required_tonnage` |

결과 (무작위 화물 10,000건): 등록된 정상 화물 7,292건 재검증 → **위반 0건** · 위반 화물 6종 1,492건 **모두 거부** · 실제 무게 기준 과적 0.32% (1-3장).
결과 (주문 8,008건 · 시드 7): 배차된 적재 계획 2,200건 재검증 → **위반 0건** (8개 시드 합계 17,328건 · 위반 0건).
위반 화물 주입: 주문의 12%(시드 7: 917건)를 과적(화주가 고른 차종 최대 적재량의 110~120%) · 편심(적재량 절반짜리 장비 1대가 적재함 앞쪽에 몰림) 화물로 바꿔 넣으면 → **등록 단계에서 917건(과적 454 · 편심 463) 모두 거부** (8개 시드 합계 7,651건 모두 거부). 정상 샘플 화물 2,483건은 하나도 잘못 막히지 않음 (8개 시드 합계 19,950건 오차단 0건).

### 4-2. 행동적 오탐 (매칭)
- 하드 필터: 관제 승인 · 사업용 노란 번호판 · `기사 톤수 ≥ 필수 최소 톤수` · 블랙리스트 제외 · PostGIS 반경
- LightGBM 수락 예측(피처 10개: 거리 · 적재율 · 운임 · 운송거리 · 콜드체인 · 긴급 · 수락률 · **cf_score · 평점 · 러시아워**, AUC 0.859)
- **lgb_score ≥ 0.75** 인 후보에게만 자동 제안 → 주문 8,008건에서 2,557쌍 차단, 거절률 2.2% (8개 시드 1.7 ~ 2.2%)

### 4-3. GPS 오탐 (디바운싱)
- 계획 경로까지 최단 거리(Shapely) > 1km 가 **연속 3회**일 때만 경고 → 단발 튐 8회 오탐 0건, 고의 이탈 4건 모두 정확히 3번째 핑에서 경고
- 실시간 시뮬레이터도 같은 두 시나리오를 섞어 보낸다: **단발 튐**(90초마다 운행 1대가 2.5km로 1~2번 튐 → 경보 없어야 정상) · **고의 이탈**(240초마다 2km로 4번 연속 → 3번째 핑에 경보)
- 배정 기사가 아닌 단말의 핑은 반영하지 않고 '불법 재위탁 의심'(HIGH)으로 기록 + 해시 체인 감사 로그

## 6. 한계

- 모든 수치는 **가상 데이터 · 단일 PC 도커** 기준. 실제 단말 GPS 는 검증하지 않음. 매칭 · 적재 KPI는 8일 · 8,008건 · 기사 400명 규모로 측정 (시드 8개, 합계 64,049건).
- 백엔드 저장소는 메모리 작업본 + PostgreSQL write-behind → 백엔드 1프로세스로만 운영 가능.
- "과적 0%"는 입력된 품목 치수 · 무게가 정확할 때, 규칙 안에서만 보장. 실제 무게가 신고보다 5% 넘게 무거우면 과적이 생길 수 있음 (무작위 화물 10,000건 · 오차 −5~+10%: 0.32%) → 계근 · 상차 검수로 보완.

```bash
python -m tests.stress_tests.stress_test --out docs/설명/benchmark_metrics.json      # 기본 (시드 7 · 하루 118건 · 기사 45명)

python backend/tests/stress_tests/4_show_results.py                                 # 실행 없이 저장된 결과를 모두 표로
python backend/tests/stress_tests/5_packing_stress.py                               # 과적 · 적재 대량 테스트: 무작위 화물 10,000건 (약 20~30분)
```

| 옵션 | 뜻 |
|---|---|
| `--target N` | 주문 생성 시도가 N건이 되면 멈추고 집계 (건수 제한) |
| `--max-minutes M` | M분이 지나면 멈추고 그때까지로 집계 (시간 제한) |
| `--days D` · `--orders N` | 하루 N건(포아송 · 러시아워)을 D일 반복 |
| `--batch B` | 배정 라운드 한 번에 묶는 주문 수 (마이크로 배치 창) |
| `--expire-hours H` | H시간(시뮬레이션) 동안 배차 안 된 주문은 만료로 집계 |
| `--detail` · `--csv-dir` | 시간대 · 날짜 · 거점 · 차종 · 분포 통계 / 주문별 · 라운드별 CSV |
